# 実装メモ（要件定義書との対応・変更点）

要件定義書の内容をもとに、本番公開に向けて Vercel ＋ Supabase で実装した際の補足です。

## 1. 要件定義書からの変更点

| 項目 | 要件定義書 | 実装 | 理由 |
|---|---|---|---|
| 開発・DB・ホスティング | GenSpark | GitHub ＋ Vercel ＋ Supabase | 本番公開の方針変更（ユーザー指示） |
| 合言葉の最低文字数 | 指定なし | **6文字以上** | Supabase Auth の仕様（パスワードは6文字以上） |
| 合言葉の保存場所 | Users テーブルの `password` | **Supabase Auth が暗号化して保管** | 合言葉を読める形で保存しないため。Users テーブルには持たない |
| 選手の合言葉 | 選手名 ＋ 合言葉 | **選手は合言葉なし（名前を選ぶだけ）。合言葉はコーチのみ** | ユーザー指示。合言葉リセット機能も削除 |
| 選手の情報 | 名前のみ | **名前・学年・ポジション（フロント／バックロー／バックス）・並び順** | ユーザー指示 |
| サンプルデータ | 初期状態から投入 | 初期設定画面で「サンプル選手も入れる」を選ぶと投入 | 本番では不要になるため選べるようにした |

「選手管理」は、約30名の選手登録のために追加しました。

- 選手は「名前・学年・ポジション」で登録します（合言葉は不要）。コーチを追加するときだけ合言葉を入力します。
- 選手の並び順は、基本は学年が上の人が上。新しく追加した選手は「同じ学年の一番下」に入ります。
- ▲▼ボタンで自由に入れ替えでき、「学年順に並べ直す」で学年順に戻せます。
- この並び順はログイン画面・チーム画面・フィジカル画面の一覧でも使われます。

## 3. データ構造（要件定義書 4章に対応）

SQL は `supabase/schema.sql`。

- `users`：id / name（ログインID兼用）/ role（player・coach）/ login_email（内部用。メールは送らない）/ grade（学年）/ position（フロント・バックロー・バックス）/ sort_order（並び順。小さいほど上）
- `daily_records`：id / user_id / date / attendance（出席・欠席）/ weight
- `physical_records`：id / user_id / date / bench_press / squat / deadlift
- 同じ人・同じ日付の記録は1件（再入力すると上書き）

## 4. 権限（RLS）

- メンバーは全員分の記録を閲覧できる（ランキング・コーチ画面のため）
- 記録の追加・修正は本人分のみ
- メンバー追加・編集・並び替え・削除はコーチのみ（サーバー側 `app/api/admin/route.ts` で確認）
- 選手のログインは、サーバー側で名前から本人を探し、使い捨てのログイン用の鍵を発行して行う（メールは送らない）。合言葉がないため、名前を選べば誰でもその選手としてログインできる点に注意

## 5. 環境変数（Vercel で設定）

| 名前 | 内容 | 公開してよいか |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase の Project URL | 可 |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Supabase の Publishable key（`sb_publishable_…`） | 可（RLSで保護） |
| `SUPABASE_SECRET_KEY` | Supabase の Secret key（`sb_secret_…`） | **不可**（サーバー側のみで使用） |
